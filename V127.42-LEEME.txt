NIÑOS RANCIOS — V127.42 POSTGRESQL + MIGRACIÓN JSON
Base: V127.41 — Seguridad / Preproducción
Estado: PREPRODUCCIÓN

OBJETIVO
Iniciar la sustitución segura de los archivos JSON críticos por PostgreSQL sin rehacer el frontend ni revertir las protecciones de V127.41.
Esta versión está pensada especialmente para un despliegue posterior en Railway con PostgreSQL.

QUÉ SE MIGRÓ A LA NUEVA CAPA DE PERSISTENCIA
Cuando DATA_BACKEND=postgres, PostgreSQL pasa a ser la fuente de verdad para:
- orders.json
- inventory.json
- customers.json
- customer-sessions.json
- payment-drafts.json
- promotion-usage.json

Los JSON originales NO se eliminan. El script de migración los lee y los conserva como respaldo.

CAMBIOS PRINCIPALES
1. Nueva capa PostgreSQL:
   - server/database.js
   - server/persistence.js
   - tablas para pedidos, inventario, clientes, sesiones, borradores de pago y usos de promociones.

2. Transacciones para operaciones críticas:
   - creación de pedidos manuales + descuento de inventario;
   - finalización de Stripe/PayPal/Mercado Pago + descuento de inventario + creación del pedido;
   - cancelaciones que devuelven inventario;
   - expiración de reservas;
   - confirmación de transferencia;
   - cambios de estado que afectan inventario/promociones.

3. Restricciones UNIQUE de base de datos para reducir doble procesamiento entre procesos/instancias:
   - Stripe payment_intent_id
   - PayPal order id
   - PayPal capture id
   - Mercado Pago order/preference id
   - Mercado Pago payment id
   - clientRequestId de pedidos manuales
   - uso de promoción por pedido

4. Inventario normalizado en PostgreSQL por:
   product_id + color + size
   con cantidad >= 0 y clave primaria compuesta.

5. Clientes:
   - correo único sin distinguir mayúsculas/minúsculas mediante índice LOWER(email).
   - sesiones de cliente pasan a PostgreSQL cuando ese backend está activo.

6. Compatibilidad controlada:
   DATA_BACKEND=auto
   - si DATABASE_URL está configurada: PostgreSQL;
   - si no existe DATABASE_URL: JSON local, conservando el comportamiento de V127.41.

7. Nuevos comandos:
   npm run db:migrate
   npm run db:check

8. Script de migración:
   server/migrate-json-to-postgres.js
   - crea/verifica el esquema;
   - importa los seis JSON objetivo;
   - valida conteos antes de terminar;
   - aborta si la base ya contiene datos, salvo uso deliberado de --force;
   - no borra ni modifica los JSON de origen.

9. PostgreSQL cliente:
   pg ^8.23.1

10. Seguridad V127.41 preservada:
   - /server y /server/* siguen bloqueados;
   - Helmet y cabeceras de seguridad se mantienen;
   - trust proxy configurable se mantiene;
   - rate limiting se mantiene;
   - reservas temporales y devolución de inventario se mantienen;
   - el correo de estado Enviado sigue enviándose DESPUÉS de guardar paquetería/guía/URL;
   - no se volvió a publicar la raíz completa del proyecto.

ARCHIVOS QUE SIGUEN FUERA DE ESTA MIGRACIÓN
Se mantienen en su mecanismo anterior porque no forman parte de los seis JSON objetivo de V127.42:
- products.json y configuración visual/catálogo;
- promotions.json (definiciones; promotion-usage sí migra);
- customer-action-tokens.json;
- configuraciones de portada, correo, guía de tallas, transferencia, etc.;
- sesiones administrativas y de Colaboraciones continúan en memoria como en V127.41.

CONFIGURACIÓN RECOMENDADA EN RAILWAY
DATA_BACKEND=postgres
DATABASE_URL=<variable proporcionada por PostgreSQL/Railway>
DATABASE_SSL=false   (si se usa red privada de Railway; confirmar según el tipo de conexión elegido)
DATABASE_POOL_MAX=10
NODE_ENV=production
TRUST_PROXY_HOPS=<valor validado para la topología real>

NO inventar ni copiar credenciales de ejemplo como valores reales.

FLUJO DE MIGRACIÓN PROPUESTO
1. Crear PostgreSQL en Railway.
2. Configurar DATABASE_URL y DATA_BACKEND=postgres en un entorno de staging/preproducción.
3. Desde server/ ejecutar npm install.
4. Ejecutar npm run db:migrate una sola vez sobre una base vacía.
5. Ejecutar npm run db:check.
6. Levantar la aplicación y repetir CHECKLIST de tienda/cuentas/pedidos/pagos de prueba.
7. Mantener los JSON originales como respaldo durante toda V127.42.

IMPORTANTE SOBRE --force
npm run db:migrate -- --force
TRUNCA las seis tablas objetivo antes de reimportar. Usarlo únicamente si se quiere rehacer deliberadamente la importación y existe un respaldo confirmado.

VALIDACIONES REALIZADAS EN ESTE PAQUETE
- node --check en los archivos JavaScript modificados.
- pruebas aisladas en modo JSON para cuentas, sesiones y favoritos.
- prueba aislada de contraentrega: descuento de stock, idempotencia por requestId y restauración al cancelar.
- prueba aislada de finalización Stripe simulada: creación del pedido e idempotencia sin doble descuento de stock.

LIMITACIÓN DEL ENTORNO DE GENERACIÓN
No fue posible completar npm install dentro del entorno donde se generó este ZIP, por lo que no se generó package-lock.json y no se pudo abrir una instancia PostgreSQL real aquí.
En tu PC/Railway debes ejecutar npm install, npm run security:check y las pruebas db:migrate/db:check antes de considerar V127.42 validada contra PostgreSQL real.
